#### 1.3.3 系统代理设置（Windows）

```python
# services/proxy_service.py
import winreg

def set_system_proxy(host: str, port: int):
    """设置Windows系统代理"""
    key = winreg.OpenKey(
        winreg.HKEY_CURRENT_USER,
        r"Software\Microsoft\Windows\CurrentVersion\Internet Settings",
        0, winreg.KEY_SET_VALUE
    )
    
    # 启用代理
    winreg.SetValueEx(key, "ProxyEnable", 0, winreg.REG_DWORD, 1)
    winreg.SetValueEx(key, "ProxyServer", 0, winreg.REG_SZ, f"{host}:{port}")
    
    # 本地地址绕过
    winreg.SetValueEx(key, "ProxyOverride", 0, winreg.REG_SZ, 
                      "<local>;localhost;127.*;10.*;192.168.*")
    
    winreg.CloseKey(key)
    
    # 通知系统刷新代理设置
    internet_set_option(0, INTERNET_OPTION_SETTINGS_CHANGED, 0, 0)
    internet_set_option(0, INTERNET_OPTION_REFRESH, 0, 0)
```

### 1.4 移动端原生实现

#### 1.4.1 VpnService 生命周期

```java
// MihomoVpnService.java
public class MihomoVpnService extends VpnService {
    
    @Override
    public int onStartCommand(Intent intent, int flags, int startId) {
        // 1. 构建VPN Builder
        Builder builder = new Builder();
        builder.addAddress("10.0.0.2", 32);
        builder.addRoute("0.0.0.0", 0);
        builder.addDnsServer("8.8.8.8");
        
        // 2. 建立VPN连接
        ParcelFileDescriptor vpnInterface = builder.establish();
        
        // 3. 启动mihomo进程（TUN模式）
        startMihomoProcess(vpnInterface);
        
        // 4. 前台服务保活
        startForeground(NOTIFICATION_ID, createNotification());
        
        return START_STICKY;
    }
    
    @Override
    public void onDestroy() {
        // 清理资源
        stopMihomoProcess();
        super.onDestroy();
    }
}
```

### 1.5 版本管理机制

#### 1.5.1 硬链接版本切换

```python
# services/version_service.py
import os

def switch_version(target_path: str):
    """使用硬链接实现零延迟版本切换"""
    current_link = "app/云集智能网联代理专家.exe"
    
    # 删除旧链接
    if os.path.exists(current_link):
        os.remove(current_link)
    
    # 创建新硬链接（同一inode，不占用额外空间）
    os.link(target_path, current_link)
    
    return {"ok": True, "switched_to": target_path}
```

```python
# services/update_service.py
import asyncio
import aiohttp

async def check_updates_parallel():
    """并行检查GitHub和Gitee更新"""
    sources = [
        ("github", GITHUB_API_URL),
        ("gitee", GITEE_API_URL)
    ]

    return done.pop().result()
```

### 2.2 核心技术优势

#### 优势 1：Web化架构带来的跨平台能力

**传统方案问题：**
- PyQt6/Tkinter：只能做桌面端，手机端需要重写
- Electron：体积庞大（150MB+），内存占用高
- 原生开发：各平台独立代码，维护成本高

**云集方案：**
```
一套 Vue 3 前端代码
    ↓
┌───────────────┬───────────────┐
│  pywebview    │  Capacitor    │
│  (桌面壳)     │  (手机壳)     │
└───────────────┴───────────────┘
    ↓               ↓
 Windows EXE    Android APK
   ~38MB          ~40MB
```

**收益：**
- 代码复用率 >90%
- 新功能一次开发，多端同步上线
- 维护成本降低 60%+

#### 优势 2：pywebview 轻量集成

**与 Electron 对比：**

| 指标 | Electron | pywebview | 提升 |
|:-----|:---------|:----------|:-----|
| 安装包体积 | 150-200MB | 35-40MB | **-75%** |
| 冷启动时间 | 3-5秒 | <1秒 | **-80%** |
| 内存占用 | 200-500MB | 50-150MB | **-70%** |
| CPU占用 | 较高 | 较低 | **-50%** |

**原理：**
- Electron：内嵌 Chromium + Node.js，完整浏览器环境
- pywebview：调用系统自带 WebView2（Windows 11自带），只增加 Python 运行时

#### 优势 3：多线路并行测速 + 自动切换

**传统方案：**
- 串行检测：4条线路 × 500ms = 2秒
- 手动切换：用户发现卡顿后手动操作

**云集方案：**
```python
# 并行检测，总耗时 = 最慢线路时间
async def test_all_lines(lines):
    tasks = [test_line(line) for line in lines]
    results = await asyncio.gather(*tasks)
    return sorted(results, key=lambda x: x.latency)

# 定时自动切换
async def auto_optimize():
    while True:
        await asyncio.sleep(30 * 60)  # 每30分钟
        best_line = await find_best_line()
        await switch_to_line(best_line)
```

**收益：**
- 检测速度提升 **4倍**（并行 vs 串行）
- 用户无感知切换，始终保持最优连接

#### 优势 4：硬链接版本切换

**传统方案：**
- 复制文件：35MB × 2次读写 = 70MB IO
- 耗时：2-5秒（取决于磁盘速度）

**云集方案：**
```python
# 硬链接：同一inode，不复制数据
os.link(target_exe, current_exe)  # 耗时 <10ms
```

**收益：**
- 切换速度提升 **500倍**（10ms vs 5s）
- 磁盘空间节省 100%（多版本共享同一数据）

#### 优势 5：双源并行更新

**传统方案：**
- 单源下载：GitHub 国内访问慢，Gitee 海外无法访问
- 失败重试：超时后手动切换

**云集方案：**
```python
# 并行请求，取最快结果
github_task = fetch_github()
gitee_task = fetch_gitee()

done, _ = await asyncio.wait(
    [github_task, gitee_task],
```

**收益：**
- 更新检查速度提升 **2-5倍**（取决于网络环境）

## 三、技术选型决策记录

### 3.1 为什么选择 Web 架构而非纯原生？

**决策因素：**
1. **跨平台需求**：需要同时支持 Windows 和 Android
2. **维护效率**：避免多套代码重复开发
3. **迭代速度**：新功能快速上线

**备选方案对比：**

| 方案 | 优点 | 缺点 | 决策 |
|:-----|:-----|:-----|:-----|
| PyQt6 + Kivy | 纯Python | 手机端体验差 | ❌ |
| Electron + React Native | 成熟生态 | 体积大，维护两套UI | ❌ |
| Flutter | 真正跨平台 | 学习曲线陡，Python后端集成复杂 |  |
| **Vue 3 + pywebview/Capacitor** | **轻量、熟悉的技术栈、Python友好** | **需要平台适配层** | **✅** |

### 3.2 为什么选择 pywebview 而非 Electron？

**关键数据：**
- 体积：38MB vs 150MB（**-75%**）
- 启动：<1s vs 4s（**-75%**）
- 内存：<150MB vs 300MB（**-50%**）

**决策依据：**
- 项目不需要 Chromium 的高级特性（DevTools、扩展等）
- Windows 11 自带 WebView2，无需捆绑浏览器
- Python 后端与 pywebview 集成更自然

### 3.3 为什么选择 FastAPI 而非 Flask？

**对比：**

| 特性 | FastAPI | Flask |
|:-----|:--------|:------|
| 异步支持 | ✅ 原生 | ️ 需额外配置 |
| 自动文档 | ✅ Swagger UI | ❌ 需插件 |
| 类型检查 | ✅ Pydantic | ⚠️ 可选 |
| 性能 | 🟢 高（Starlette） | 🟡 中 |
| WebSocket | ✅ 原生 | ⚠️ 需插件 |

**决策依据：**
- 异步框架更适合 I/O 密集型任务（代理、下载）
- 自动 Swagger 文档减少接口文档维护成本
- WebSocket 原生支持实时日志推送

### 3.4 为什么选择 Capacitor 而非 React Native？

**对比：**

| 特性 | Capacitor | React Native |
|:-----|:----------|:-------------|
| 前端框架 | 任意（Vue/React/Angular） | 必须 React |
| 学习曲线 |  低（Web技术） | 🟡 中（JSX + Native模块） |
| 与现有代码复用 | ✅ 100% | ❌ 需要重写 |
| 原生插件开发 | Java/Kotlin | Java/Kotlin + JS桥接 |
| 社区生态 | 🟡 中等 | 🟢 成熟 |

**决策依据：**
- 已有 Vue 3 前端代码，Capacitor 可直接复用
- React Native 需要重写整个前端
- Capacitor 插件开发与 RN 类似，但前端零改造
