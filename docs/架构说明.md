## project.json 单一数据源架构

### 设计目标

- 所有路径、命名、仓库信息由 `project.json` 统一驱动
- 代码中不硬编码这些值，修改目录结构只需编辑 JSON
- 兼容旧版本 EXE（无 project.json 时自动回退）
- 零兼容代码——回退机制内嵌于读取函数，不增加额外逻辑

### 配置结构

```json
{
    "brand_name": "云集智能网联代理专家",
    "repos": {
        "github": "yunjii-cn/ip",
        "gitee": "yunjii/ip",
        "mihomo": "MetaCubeX/mihomo"
    },
    "paths": {
        "version_json": "release/version.json",
        "dev": "dev",
        "app": "app",
        "ver": "ver",
        "dist": "dist",
        "build": "build",
        "release": "release",
        "lock_file": ".yunji.lock"
    }
}
```

### 字段说明

| 字段 | 用途 | 示例 |
|------|------|------|
| `brand_name` | 品牌名称，用于 UI 显示和文件命名 | 云集智能网联代理专家 |
| `repos.github` | GitHub 仓库路径，用于更新检查和 Release 下载 | yunjii-cn/ip |
| `repos.gitee` | Gitee 仓库路径，国内直连备用 | yunjii/ip |
| `repos.mihomo` | mihomo 内核仓库路径，用于内核版本获取 | MetaCubeX/mihomo |
| `paths.version_json` | version.json 相对于项目根的路径 | release/version.json |
| `paths.dev` | 开发目录名 | dev |
| `paths.app` | 应用源码目录名 | app |
| `paths.ver` | 版本仓库目录名 | ver |
| `paths.dist` | 构建产物统一输出目录（**项目根 `dist/`**，2026-08-16 起约定） | dist |
| `paths.build` | 构建目录名 | build |
| `paths.release` | 公开发布目录名 | release |
| `paths.lock_file` | 路径定位标记文件名 | .yunji.lock |

### 三级回退机制

`_load_project_config()` 函数按以下优先级读取配置：

```
┌──────────────────────────────────────────────────────┐
│ 1. EXE 模式                                          │
│    读取 PyInstaller 捆绑的 project.json               │
│    路径: sys._MEIPASS / project.json                  │
│    （构建时 --add-data=project.json;. 打包）           │
├──────────────────────────────────────────────────────┤
│ 2. 源码模式                                          │
│    读取项目根目录的 project.json                       │
│    路径: PROJECT_ROOT / project.json                  │
├──────────────────────────────────────────────────────┤
│ 3. 内嵌默认值                                        │
│    读取失败时使用 _DEFAULTS 字典                       │
│    （旧版 EXE 无 project.json 时自动回退）             │
│    零兼容代码——不需要任何版本判断逻辑                  │
└──────────────────────────────────────────────────────┘
```

### 代码中使用方式

```python
_CFG = _load_project_config()

VERSION = ...  # 版本号仍由构建脚本注入
GITHUB_REPO = _CFG["repos"]["github"]
GITEE_REPO = _CFG["repos"]["gitee"]
MIHOMO_REPO = _CFG["repos"]["mihomo"]
VERSION_JSON_PATH = _CFG["paths"]["version_json"]
BRAND_NAME = _CFG["brand_name"]

# 路径使用示例
ver_dir = os.path.join(dev_dir, _CFG["paths"]["ver"])
app_dir = os.path.join(dev_dir, _CFG["paths"]["app"])
lock_file = os.path.join(dev_dir, _CFG["paths"]["lock_file"])
```

### 构建脚本同步

`build/build.py` 和 `build/release.py` 同样通过各自的 `_load_project_config()` 读取配置，确保：
- 构建输出路径与运行时路径一致
- 发布脚本使用正确的仓库信息
- 品牌名称在构建和运行时统一

### 扩展指南

添加新配置项时：
1. 在 `project.json` 中添加字段
2. 在 `_DEFAULTS` 字典中添加对应默认值
3. 在代码中通过 `_CFG["new_field"]` 读取

修改目录结构时：
1. 只需编辑 `project.json` 中的 `paths` 字段
2. 无需改动任何代码
3. 重新构建 EXE 即可生效

## 代理内核状态系统

### 设计目标

- 首页实时显示代理内核状态，内核是软件能否正常工作的硬指标
- 首次启动时自动下载内核，让用户感知这是正常初始化流程而非功能缺失
- 下载过程中显示进度条，让用户知道进展

### 状态定义

| 状态标识 | 首页文案 | 颜色方案 | 进度条 | 触发条件 |
|---------|---------|---------|--------|---------|
| `ready` | ✅ 代理内核已启用 | 绿色 (#1a3a2a) | 隐藏 | 内核已安装 |
| `initializing` | ⏳ 获取新版代理内核... | 蓝橙色 (#1a2a3a) | 隐藏 | 首次启动，正在获取版本信息 |
| `downloading` | ⏳ 下载代理内核 vX.X.X... | 蓝橙色 (#1a2a3a) | 显示 | 正在下载内核文件 |
| `failed` | ⚠ 代理内核下载失败，请在代理设置中获取更新 | 红色 (#3a1a1a) | 隐藏 | 下载失败 |
| `missing` | ⚠ 代理内核缺失，点击修复 | 红色 (#3a1a1a) | 隐藏 | 内核缺失且非自动下载场景 |

### 状态流转

```
应用启动
  │
  ├─ 内核已安装 → ready
  │
  ├─ 内核缺失 + _auto_download_kernel=True
  │   │
  │   ├─ 启动自动下载 → initializing
  │   │   │
  │   │   ├─ 获取版本列表成功 → downloading（显示进度条）
  │   │   │   │
  │   │   │   ├─ 下载完成 → ready
  │   │   │   └─ 下载失败 → failed
  │   │   │
  │   │   └─ 获取版本列表失败 → failed
  │   │
  │   └─ （自动下载由 QTimer.singleShot 延迟启动）
  │
  └─ 内核缺失 + _auto_download_kernel=False → missing
```

### 核心方法

| 方法 | 职责 |
|------|------|
| `_update_kernel_status()` | 根据当前内核状态和 `_auto_download_kernel` 标志，调用 `_set_home_kernel_status()` 设置首页状态 |
| `_set_home_kernel_status(state, text)` | 统一更新首页 `svc_kernel_status` 标签和 `svc_kernel_progress` 进度条 |
| `_on_home_kernel_download_percent(pct)` | 接收 `KernelDownloadWorker.download_percent` 信号，更新进度条 |
| `_auto_download_latest_kernel()` | 启动自动下载流程，连接信号到首页 |
| `_on_auto_kernel_versions_fetched()` | 版本列表获取完成，启动下载 |
| `_on_auto_kernel_download_finished()` | 下载完成/失败，更新首页状态 |

### 信号连接

```
KernelVersionWorker
  ├── progress(str)         → kernel_status（内核页面状态标签）
  └── finished(list, str)   → _on_auto_kernel_versions_fetched

KernelDownloadWorker
  ├── progress(str)              → kernel_status（内核页面状态标签）
  ├── download_percent(int)      → _on_home_kernel_download_percent（首页进度条）
  └── finished(bool, str, str)   → _on_auto_kernel_download_finished
```

### UI 组件

首页状态栏中的内核相关组件：

```
[内核: v1.19.25] [✅ 代理内核已启用] [████████░░ 80%] [线路: xxx] [🔍 检测线路]
                  ↑ svc_kernel_status   ↑ svc_kernel_progress（仅下载时显示）
```

## 代理内核版本管理

### 内核文件结构

```
Quick/
├── quick.exe                   # 当前使用的内核（硬链接或复制）
├── _kernel_version.txt         # 内核版本标记（如 "1.19.25"）
└── kernels/                    # 内核版本仓库
    ├── mihomo_v1.19.25.exe     # 稳定版
    ├── mihomo_v1.19.26.exe     # 稳定版
    └── mihomo_1.26.3.exe       # 预览版（Alpha）
```

### 版本切换机制

切换内核时：
1. 停止正在运行的代理服务
2. 将目标版本复制为 `quick.exe`（覆盖当前）
3. 更新 `_kernel_version.txt`
4. 如果代理之前在运行，自动重启

### mihomo 版本命名规则

mihomo 内核的版本号有特殊规则，需特别注意：

| 类型 | 格式 | 示例 | 说明 |
|------|------|------|------|
| 稳定版 | `v` + 三段式 | v1.19.25 | 经过测试的正式版本 |
| 预览版 | 无 `v` 前缀，数字可能更大 | 1.26.3 | Alpha 预发布版，数字可能大于稳定版但不稳定 |

**关键点**：预览版数字可能大于稳定版（1.26.3 > 1.19.25），但这不代表预览版更新或更稳定。稳定版才是经过完整测试的版本。

### 预览版开关

- 位于代理内核页面，`ToggleSwitch("预览版")`，默认关闭
- 关闭时：版本列表只显示稳定版（`prerelease=False`）
- 开启时：版本列表额外显示预览版，并提示"含 X 个预览版，开启预览版开关可见"
- 自动下载始终选择最新稳定版，不受预览版开关影响

### 内核下载策略

`KernelDownloadWorker` 按优先级尝试多种下载方式：

```
1. GitHub 加速镜像
   ├── gh-proxy.com
   ├── ghproxy.net
   ├── ghproxy.homeboyc.cn
   ├── ghfast.top
   └── mirror.ghproxy.com

2. 本地代理直连（如果代理正在运行）
   └── 使用 http://{PROXY_URL} 作为代理

3. 系统代理直连（如果系统代理已配置）
   └── 使用系统代理设置

4. GitHub 直连
   └── 无代理，直接连接
```

每种方式尝试下载，文件大小 > 1000 字节视为成功，否则尝试下一种。

## 双源并行更新机制

### 软件版本更新

检查更新时并行请求 Gitee 和 GitHub，谁先返回用谁：

| 来源 | URL | 特点 |
|------|-----|------|
| Gitee | `gitee.com/api/v5/repos/{repo}/contents/release/version.json` | 国内直连，速度快 |
| GitHub | `raw.githubusercontent.com/{repo}/main/release/version.json` | 需代理，但更稳定 |

### 代理内核版本获取

内核版本列表从 `MetaCubeX/mihomo` 的 GitHub Releases 获取：
- URL: `https://api.github.com/repos/MetaCubeX/mihomo/releases`
- 自动识别 Windows amd64 对应的 zip 资源
- 解析版本标签区分稳定版和预览版

### 下载源选择

- 软件版本 EXE：根据版本检查的来源（Gitee/GitHub）自动选择对应的 Releases
- 代理内核：通过 GitHub 加速镜像下载，失败后回退到代理直连和直连

## 构建、发布与目录约定

### 目录职责（2026-08-16 起统一约定）

| 目录 | 职责 |
|------|------|
| `dist/`（**项目根**） | 构建产物统一输出目录：`云集智能网联代理专家-v<时间戳>.exe` + 整合包 staging。每次 `build/build.py` 生成。 |
| `dev/ver/` | 正式发布版仓库：确认稳定后把 `dist/` 的 EXE 移入此处；`dev/云集智能网联代理专家.exe` 硬链接指向最新 ver。 |
| `release/version.json` | 远程更新检查用的版本清单（由 `release.py` 生成）。 |
| `build/v<时间戳>/` | 单次构建的中间 staging（整合包、备份脚本等）。 |

> 约定变更：此前构建产物落 `dev/dist/`，2026-08-16 起统一改为**项目根 `dist/`**。`build.py` 的 `dist_dir` 与 `release.py` 的 `step_stabilize`/`step_get_version` 已同步指向 `PROJECT_ROOT/dist`。

### 全自动发布（`build/release.py`）

`release.py` 一次性完成：内核校验 → 收集变更 → 构建 → 稳定化(dist→ver) → 生成 version.json → **Git 推送双仓库**（`origin`=GitHub `yunjii-cn/ip`、`gitee`=Gitee `yunjii/ip`）→ 创建 **GitHub Release** → 创建 **Gitee Release（即下载页，上传 EXE）**。

- 已手动把稳定版移入 `dev/ver/` 后再发布：用 `python build/release.py --use-ver`（跳过构建/稳定化，直接以 ver 中 EXE 为准）。
- Gitee Release 需要 `dev/app/.gitee_token`（Gitee 个人访问令牌，属 `ifany` 账号）。
- Git 双仓库推送需要本机配置好 `origin`(SSH) 与 `gitee`(带 token 的 URL 或 credential helper) 凭据，且能联网。
- `dist/`、`*.exe` 均被 `.gitignore` 忽略，EXE 不进 Git 仓库，只走 Releases 下载页。

### EXE 部署内核自愈铁律（dev 能起、EXE 起不来的根因）

1. **dev 与 EXE 用同一份内核**：解包 EXE 确认内嵌 `Quick/` 与 dev 源逐字节大小完全一致，封装无缺文件、无截断。
2. **唯一实质差异是运行目录环境（非封装、非用户操作）**：
   - dev：内核直接读 `dev/app/Quick`（开发目录，Defender 通常不扫描）→ 文件始终完好 → 顺利加载 → 绑 7890。
   - EXE：内核从 `_MEIPASS` 复制到**部署目录** `Quick` 再跑；部署目录（下载目录/解压目录）被 Windows Defender **实时防护**扫描，只读数据（`geoip.metadb`/`Country.mmdb`/`quick.exe`）可能在运行时被隔离成 0 字节/损坏 → 内核卡在 `Start initial compatible provider` 或进程拉不起来 → 7890 不绑。
3. **日志与界面是两套判断机制（已证实，应以界面为准）**：
   - 日志"已启动代理内核"（`start_quick`）= 进程 spawn 成功（宽松）。
   - 界面"运行中"（`is_proxy_running` 查 7890 端口）= 端口真绑（严格）。
   - 进程起 ≠ 端口绑。dev 两者皆真；EXE 进程起但端口不绑 → 表现为"内核未启动"。
4. **代码自愈（已写入 `dev/app/main.py`，2003+ 版生效）**：
   - `_launch_quick`（主代理+检测共用唯一入口）在 `Popen` 前统一调 `_ensure_mmdb`，启动前强制还原 `geoip.metadb` + `Country.mmdb`。
   - `_restore_bundled_kernel` 对只读数据文件强制覆盖，并加**完整性校验**（部署文件体积 < 内嵌源 90% 即强制重覆盖，覆盖集含 `quick.exe`）。
   - `quick.exe` 入口自检+自愈（体积异常偏小立即从内嵌副本重还原）。
5. **验证铁律**：彻底删除旧部署目录后全新双击 + 把 EXE 目录加入 Windows 安全中心「排除项」（根治 Defender 实时隔离）。本地沙箱复现已证 config 合法、内核加载成功（`Initial configuration complete`，无 geoip 报错）。
6. **仍"未启动"时取证**：贴 `EXE_DIR/Quick/quick_out.log`（内核真实报错，非应用日志）+ `EXE_DIR/Quick/config.yaml` 全文 + `quick.exe` 部署后实际字节数（正常≈53MB，被隔离=几 KB/0）。
